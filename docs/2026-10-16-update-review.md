# 2026-10-16 세 파일 통합 및 업데이트 분석

## 통합 결과

`gui.py`, `model.py`, `monitor.py`의 구현을 `gui.py` 한 파일로 통합했다. `model.py`와 `monitor.py`는 제거했고, 운영 모듈 8개와 관련 테스트의 import를 변경했다. 실행 경로는 `main.py` / `run_hwadam.vbs` 그대로다. API·브라우저·저장·레이아웃 파일과 이미지·상품 데이터는 여전히 함께 필요하다.

| 수정 대상 | 통합 파일의 구역 / 정의 |
| --- | --- |
| 감시 날짜·권종·수량·주기·재고 판정 | 1. 감시 모델·재고 판정 / `WatchConfig`, `Availability`, `evaluate_round` |
| 감시 반복·알림 변화 판정·텔레그램 이벤트 | 2. 감시 루프·알림 / `AlertTracker`, `MonitorRunner` |
| 옵션·날짜·시간·결제 화면 동작 | 3. 브라우저 예약 테스트 / `run_test_booking` |
| 관리 화면·시나리오·테스트 시작 | 4. 결제 준비·관리 화면 / `OperationsUI` |
| 앱 시작·설정·작업 큐·감시 화면 | 5. 설정 변환·앱 제어 / `App` |

순환 import를 피하기 위해 API·브라우저·저장 의존성은 해당 함수 안에서 불러온다. 모델과 감시 클래스는 중복 없이 `gui`에만 존재한다. 이번 업로드에서 빠진 관리 화면 기본 선택도 복원했다: 화면 진입 또는 관리 모드 열기 시 `1장 부분 가용` / `전체 결제 (PIN까지)`가 선택된다. 진행 중인 GUI 미리보기의 선택값은 유지한다.

브라우저 오른쪽 40% 배치, 기존 GUI 크기, 저장 시 `NOL_MON_PIN` 보존 기능은 유지했다. GUI 검증에는 `auto_open_browser=False`를 사용하고 `--gui-smoke`에서도 자동 브라우저 연결을 예약하지 않는다.

## 이번 사용자 업데이트의 변화

- `WatchConfig` 기본 조회 주기가 10초에서 2초로, 허용 최솟값이 3초에서 2초로 바뀌었다. 저장된 설정이 있으면 그 값이 우선한다. CLI `--probe`의 기본값 10초는 별도로 남아 있다.
- 예약 함수에 옵션 열기, 날짜 선택, 시간·요금·NOL 머니 선택 재시도와 밀리초 로그가 추가되었다.
- 최종 결제 버튼 클릭, 새 결제 창 탐색, PIN 키패드 인식, `settings.json` / 환경변수의 `NOL_MON_PIN` 사용, 확인 버튼과 완료 문구 탐색이 포함되었다.
- 감시 루프가 텔레그램 전송 후 `booking_attempt` 이벤트를 발생시키도록 바뀌었다.

## 확인된 문제

아래는 업로드된 코드에 이미 있던 동작이다. 이번 통합에서는 결제 흐름이나 자동 예약의 의미를 임의로 바꾸지 않았으며, 실제 브라우저·계정·PIN·결제로 검증하지 않았다.

### P1 — 결제 중지 설정과 실제 클릭이 다름

`run_test_booking`은 `stop_before_pay=True`를 요구하고 False이면 거부하지만, True 경로에서 `click(pay_button)`과 `click(confirm)`까지 실행한다. 관리 화면과 작업 완료 로그는 계속 ‘최종 결제 미실행’이라고 표시한다.

가짜 브라우저 회귀 테스트 `BookingFlowTests.test_ready_checkout_never_clicks_final_payment`에서 최종 결제 클릭 횟수는 **1**, 기대값은 **0**으로 확인되었다. 이 테스트를 완화하거나 성공으로 표시하지 않았다. ‘결제 직전’과 ‘전체 결제’를 실제 실행 인자에 어떻게 연결할지 먼저 정리하고, 완료 상태도 준비 완료 / 결제 진행 / 예약 완료로 구분해야 한다.

### P1 — 날짜를 정확히 확인하지 못함

날짜 선택은 연·월을 제외한 일 숫자만 추출하고 모든 버튼의 본문·aria-label을 부분 검색한다. 예를 들어 1일은 10일·11일 등과도 일치할 수 있다. 날짜 버튼을 못 찾아도 ‘이미 선택된 상태’로 가정하고 다음 단계로 진행한다.

실제 달력의 연·월과 선택 날짜를 확인하고, 정확한 날짜 선택을 검증한 뒤 시간 선택으로 넘어가야 한다. 현재는 올바른 이용 날짜가 보장되지 않는다.

### P1 — 자동 예약은 이벤트만 있고 실행되지 않음

`MonitorRunner._run`은 `booking_attempt`를 내보내지만 예약 처리 블록은 `pass`이고, `App._event`의 핸들러도 로그와 TODO만 있다. ‘예약 시도 후 감시 계속’이라는 로그가 실제 예약 실행을 증명하지 않는다. 수량 확보·잔여 목표 차감·구매 완료 시 감시 중단도 연결되어 있지 않다.

추가로 이벤트는 텔레그램 전송 성공 뒤에만 발생한다. 향후 예약을 연결하더라도 텔레그램 실패에 예약이 종속되고, 알림 ACK 후 예약 실패 시 동일 재고에서 재시도하지 못할 수 있으므로 예약 상태와 알림 상태를 분리해야 한다.

### P2 — 실패나 미확인 상태도 성공으로 반환함

키패드 없음, PIN 미설정, 확인 버튼 없음, 예약 완료 화면 미확인인 경로에서 모두 True를 반환한다. 완료 문구를 읽지 못한 경우를 ‘예약 완료’와 같은 성공 결과로 취급할 수 없다. 화면 단계별 결과와 최종 예약 성공 여부를 별도로 전달해야 한다.

### P2 — PIN 입력 실패 뒤에도 확인을 시도함

숫자 버튼이 없으면 다음 자리로 넘어가고, 클릭 실패도 기록만 한 뒤 계속한다. 실제 여섯 자리 입력 여부와 무관하게 ‘PIN 6자리 클릭 완료’와 확인 버튼 클릭으로 진행한다. 실패 시 중단하고 입력 결과를 확인하는 경로가 필요하다.

### P2 — 선택자와 실행 대상이 넓거나 제한적임

- NOL 머니 선택자의 `//div[contains(., "NOL 머니")]`는 결제 수단 자체 대신 상위 컨테이너를 선택할 수 있다.
- 예약 함수는 설정의 첫 시간과 첫 권종만 사용하며, 발견한 가용 회차와 반드시 일치하지 않는다.
- 구매 수량은 현재 브라우저 선택값을 사용한다. GUI의 수량 시나리오와 결제 단계 콤보박스는 현재 브라우저 예약 호출에 연결되어 있지 않다.
- 실제 예약 테스트는 입장권 모드만 지원한다. 모노레일 동시/추가 구매, 목표 수량 분할 확보까지 완성된 상태가 아니다.

### P2 — 로그인 유지 대기와 종료 타이머

`test_booking_hold`를 해제하는 30초 타이머는 작업 완료가 아니라 작업 제출 시점부터 시작한다. 긴 예약 작업 후 결과 페이지에 머물러야 할 시간을 보장하지 못한다. 이 타이머는 종료 시 취소되지 않아 여러 GUI를 생성·종료하는 테스트에서 Tk `invalid command name ...<lambda>` 경고도 관찰되었다.

### P2 — 결제 화면 로그에 민감한 정보가 포함될 수 있음

새 결제 창 주소 앞부분과 주문번호 등을 포함한 결과 화면 일부를 로그로 남긴다. 현재 `sanitize`가 처리하는 봇 토큰·`orderGroupId` 외의 결제 URL 인자나 주문 정보는 가려지지 않을 수 있다. 원본 주소 대신 호스트/화면 종류, 주문번호 대신 성공 여부처럼 제한된 진단값을 기록하는 것이 필요하다.

## 검증 범위

- 총 **158개 중 157개 통과, 1개 실패**: 오프라인 테스트 156개 중 155개 통과 / 배포 테스트 2개 통과. 오류와 건너뛴 테스트는 없다.
- 유일한 실패는 `test_booking.BookingFlowTests.test_ready_checkout_never_clicks_final_payment`다. 위 P1 항목의 기존 결제 중지 계약 불일치로, 최종 결제 버튼 클릭 횟수는 기대 0회 / 실제 1회다. 통합 완료와 별개로 이 예약 동작은 수정이 필요하다.
- 삭제된 두 모듈 없이 각 운영 모듈 12개를 서로 다른 최초 import 대상으로 로딩하는 검증 통과.
- 임시 배포 폴더에서 GUI `1360×920`, `1160×740` 실행·주요 버튼·로그 표시 검증 통과.
- 실제 GUI 테스트는 자동 브라우저 연결을 끄고 임시 설정을 사용한다.
- 예약 가짜 브라우저는 PIN 화면을 제공하지 않는다. 실제 사용자 설정 읽기·네트워크·브라우저 실행을 차단한 검증에서 최종 결제 클릭 불일치를 재현했다.
- 실제 NOL 사이트에서 날짜 선택, 구매 수량, 결제/PIN, 예약 성공을 검증한 결과는 아니다.
